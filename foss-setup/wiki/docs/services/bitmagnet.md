## About

Bitmagnet is a self-hosted BitTorrent DHT crawler + metadata index that acts as a LOCAL Torznab indexer for Prowlarr and the *arr stack — an indexer-redundancy hedge (seed-12). It runs on the NAS (Synology DS920+, `192.168.10.4`) via DSM Container Manager / Docker Compose (project `bitmagnet`), reachable at https://bitmagnet.tabaska.us (LAN `http://192.168.10.4:3333`). WHY it exists: the public indexers the arrs rely on are rate-limited and fragile — IPTorrents caps at roughly 600 grabs/day, EZTV/The Pirate Bay throttle and periodically go dark — so if they choke, Prowlarr is left without a source. Bitmagnet answers that by continuously crawling the public BitTorrent DHT and harvesting torrent **metadata only** (infohash + name + file list + size); it has no query cap, no Cloudflare challenge, and — because it is an INDEX, not a download client — it never downloads or seeds torrent CONTENT (that is its designed function, and the reason it is safe to run 24/7). It lives on the NAS co-located with Prowlarr and the arrs so the Torznab hop is a LAN request. The stack is two containers: `bitmagnet` (image `ghcr.io/bitmagnet-io/bitmagnet:latest` digest-pinned `@sha256:cf2c16fa…`, supply-chain posture, pulled on the NAS 2026-07-28), launched as `worker run --all` so it runs the DHT crawler + the queue/classifier + the HTTP/Torznab/GraphQL server together; and `bitmagnet-postgres` (image `postgres:16-alpine` digest-pinned `@sha256:57c72fd2…`, `shm_size: 1g`, `shared_buffers=256MB`) — Bitmagnet REQUIRES Postgres, SQLite is not supported. The DB is container-only (NOT published) with its password in `/volume1/docker/bitmagnet/.env` (`POSTGRES_PASSWORD`, vault `bitmagnet.postgres_password`); its data lives on a writable bind mount at `/volume1/docker/bitmagnet/postgres`. Ports: `3333` serves the web UI + `/torznab` + `/graphql`; `3334` (TCP+UDP) is the DHT node, published so the crawler pulls inbound DHT peers and ingests faster. No TMDB API key is configured, so content classification (movie/tv enrichment) is skipped — but Torznab keyword search works on the raw torrent-name index without it (adding `TMDB_API_KEY` later would enrich results). Wiring into Prowlarr: added as a **Generic Torznab** indexer named `Bitmagnet (DHT)` — URL `http://192.168.10.4:3333/torznab`, API Path `/api`, API Key = any non-empty value (Bitmagnet does not authenticate Torznab, but Prowlarr's form requires a value; vault `bitmagnet.torznab_apikey`). Access is LAN/tailnet-only through the mini's Caddy (`reverse_proxy {$NAS_IP}:3333`, `import local_tls`, Let's Encrypt via Cloudflare DNS-01). **DEMOTED to interactive-only (fix-50, 2026-08-02):** a DHT crawler indexes whatever the swarm carries — which is dominated by low-quality re-encodes and foreign-audio dub rips — and with RSS + Automatic Search on, radarr auto-grabbed junk ~hourly and sonarr ~every 30 min, filling the movie library with Russian/Bulgarian dubbed copies of already-owned titles (fleet-sweep SC2). It is now scoped to **manual/interactive search only**: a dedicated Prowlarr **App Sync Profile "Interactive-Only (fix-50)"** (`enableRss=false`, `enableAutomaticSearch=false`, `enableInteractiveSearch=true`) is assigned to the Bitmagnet indexer, and Prowlarr's full-sync propagates those flags to every arr (radarr/sonarr Bitmagnet indexer now shows RSS off / Automatic Search off / Interactive Search on). It survives as the throttle-day fallback the operator reaches for by hand, without ever auto-grabbing. Content — not liveness — is watched by FOUR consumer-end verification checks (all `warn`, `media-indexers.yaml`): `bitmagnet-dht-ingesting` asserts the crawler wrote NEW torrents to its Postgres in the last 30 minutes (a dead crawler = a frozen, useless index); `bitmagnet-torznab-via-prowlarr` runs a real keyword search THROUGH Prowlarr scoped to the indexer requiring > 0 hits — time-boxed (`timeout: 90`, inner curls `-m`) so it reports true state instead of dying at the runner budget (SM6/SM27); `bitmagnet-demoted-interactive-only` is the fix-50 REGRESSION guard, asserting RSS + Automatic Search stay disabled in both radarr and sonarr so the auto-grab path cannot silently reopen on a re-sync; and `arr-grab-source-not-storming` is the CLASS tripwire, failing if any *auto-grab-enabled* indexer monopolises the recent grab stream (a live junk-grab storm from Bitmagnet or any future runaway indexer). At deploy the pipeline was proven end-to-end: within minutes the DHT crawler ingested thousands of torrents (0 → 1128+ and climbing), 232 were classified into searchable content, a `1080p` Torznab query returned real titles with magnet links, and the Prowlarr indexer test passed with a scoped search returning 5 real results.

## Troubleshooting

- **The arrs are auto-grabbing junk again (foreign-audio dubs, re-encodes) — `bitmagnet-demoted-interactive-only` or `arr-grab-source-not-storming` is failing** — Bitmagnet's auto-grab path has reopened — almost always because its Prowlarr **App Sync Profile** got flipped back to `Standard` (or the `Standard` profile itself was edited to enable RSS/Automatic Search). Re-apply the fix-50 demotion: in Prowlarr → Settings → Apps → **Sync Profiles**, confirm a profile **"Interactive-Only (fix-50)"** exists with `Enable RSS` OFF, `Enable Automatic Search` OFF, `Enable Interactive Search` ON; then Indexers → **Bitmagnet (DHT)** → set its Sync Profile to that profile and Save; Prowlarr re-syncs it to the arrs. Verify with `arr-grab-indexer-share.py demoted` (expect `DEMOTED_OK radarr=rss:F/auto:F sonarr=rss:F/auto:F`). If junk already imported, purge via each arr (delete the movie file + blocklist the grab) — see the fleet-sweep-2026-08-02 SC2 remediation. API path: `PUT /api/v1/indexer/<id>` with `appProfileId` set to the interactive-only profile, then `POST /api/v1/command {"name":"ApplicationIndexerSync"}`.
- **Prowlarr's Bitmagnet indexer tests OK but searches return zero results** — Bitmagnet's Torznab searches its CLASSIFIED content, which lags DHT discovery — right after deploy the raw `torrents` table fills fast but `torrent_contents` (what Torznab reads) trails while the classifier processes the queue. Give it a few minutes and re-test. Confirm ingestion + classification are both moving: `ssh nas` then `sudo /usr/local/bin/docker exec bitmagnet-postgres psql -U postgres -d bitmagnet -tAc 'SELECT count(*) FROM torrents; SELECT count(*) FROM torrent_contents;'` — both should climb. A raw check that bypasses classification: `curl -s 'http://192.168.10.4:3333/torznab/api?t=search&q=1080p' | grep -c '<item>'`.
- **The DHT crawler is not ingesting — `torrents` row count is flat / `bitmagnet-dht-ingesting` fails** — Check the crawler actually started: `sudo /usr/local/bin/docker logs --tail 30 bitmagnet` should show `started worker {"key": "dht_crawler"}` with no panics. The crawler needs UDP reachability for the DHT — confirm port `3334/udp` is published (`docker ps` shows `3334->3334/udp`) and not blocked. A fresh container spends the first ~30s running Goose migrations before the workers start; wait past that. If it truly ingests nothing, restart the stack: `cd /volume1/docker/bitmagnet && sudo /usr/local/bin/docker compose restart bitmagnet`.
- **`bitmagnet-postgres` container will not start — "Bind mount failed: /volume1/docker/bitmagnet/postgres does not exist"** — Docker on Synology does NOT auto-create bind-mount source directories. Create it first: `sudo mkdir -p /volume1/docker/bitmagnet/postgres` then `cd /volume1/docker/bitmagnet && sudo /usr/local/bin/docker compose up -d`. The Postgres image chowns the directory to its own uid on first init, so no manual ownership is needed.
- **The NAS is I/O-saturated / the arrs are throwing 'database is locked' and `nas-io-pressure` is firing — is bitmagnet the cause?** — bitmagnet's always-on DHT crawler was the #2 steady disk writer on the NAS (~3 MB/s into a 1.78M-row / 13 GB Postgres), a top contributor to the chronic I/O saturation that starves the arrs' SQLite (fix-55/SM35). fix-50 only demoted its Prowlarr *grab* posture; the crawl RATE was untouched until fix-55 set `DHT_CRAWLER_SCALING_FACTOR=3` (default 10) in `/volume1/docker/bitmagnet/docker-compose.yml` (+ the repo mirror), cutting the write rate ~3x while still ingesting thousands/30min (`bitmagnet-dht-ingesting` stays green). NB the env->config mapping has NO prefix — it is `DHT_CRAWLER_SCALING_FACTOR`, not `BITMAGNET_*` (verify with `sudo /usr/local/bin/docker exec bitmagnet bitmagnet config show | grep scaling_factor`, expect VALUE=3 FROM=env). To throttle harder drop it toward 1; if the index needs to fill faster (e.g. rebuilding), raise it and watch `nas-io-pressure`. blkio bandwidth caps are NOT an option — the Synology kernel has the blkio controller stubbed (no throttle/accounting cgroup files), so the only lever is crawl rate.
